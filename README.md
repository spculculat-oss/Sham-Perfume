1. أمر `build:pages` يبني المصدر الحالي إلى `docs` بمسار `/Sham-Perfume/`، وينشئ `404.html` متوافقًا و`.nojekyll`.

3. بيانات الأخبار المضمّنة المحدثة وترجماتها تتقدم على النسخ القديمة المحفوظة في المتصفح. تُزال سجلات التحديث المحلي التي كانت تُنشأ عند فشل الطلبات، وتُرفض البيانات غير الصالحة وتكرار المعرّفات.
4. صور الأخبار تستخدم أصول البناء الحالي، لا مسارات `/src` أو ملفات hashed من بناء قديم.
5. نسخة Pages توضح أن المحادثة وتحديث الأخبار يحتاجان خادمًا، وتعطّل هذه الطلبات بدل إظهار وعود مضللة بالمحاولة المتكررة.
6. الطلبات غير الناجحة أو التي تعيد HTML بدل JSON تظهر كأخطاء. فشل تحديث الأخبار في المتصفح أو الخادم لا يضيف خبرًا مصنوعًا ولا يُظهر نجاحًا كاذبًا.
7. الخادم يدعم `PORT` المقدم من الاستضافة، ويعيد JSON 404 لمسارات API غير الموجودة، ويعرض حالة مفاتيح الخدمات الحقيقية في `/api/models`.

## Sham Core — مساعد الخدمات ولوحة الإدارة

هيكل ذكاء اصطناعي خاص بشام، معمول من الصفر، وبيستقبل الزوار في كل الخدمات: الأدوات، المتجر، العطور المخصصة، الجملة B2B، الاستشارات، والدعم. **بيشتغل من غير أي مفتاح**: التوجيه والاسترجاع والأدوات والذاكرة كلها داخلية. ولو حبيت تضيف نموذج لغوي، تقدر تستخدم نموذج مفتوح مستضاف ذاتياً (Ollama أو vLLM) أو أي مزود خارجي، والتبديل بينهم تلقائي لو واحد فشل. الشرح الكامل ودراسة منصات ChatGPT وClaude وGemini وDeepSeek وManus موجودين في [`SHAM_CORE.md`](SHAM_CORE.md).

- الزائر: زر «مساعد شام للخدمات» في الركن المقابل لشاهين. منه بيعمل الطلبات بسلة أسعارها محسوبة على الخادم، ويتتبع طلبه برقم الطلب مع الهاتف أو البريد، ويتحول لموظف ويستلم رده في نفس المكان.
- الإدارة: `/#admin` باستخدام `SHAM_ADMIN_TOKEN`. فيها الطلبات، والمحادثات والرد عليها، والمنتجات، وقاعدة المعرفة، وإضافة خدمات تجارية جديدة من غير كود، وترتيب المحركات، ومختبر بمسار التنفيذ.
- التخزين: `SHAM_STORE=file` على Node/VPS، و`SHAM_STORE=firestore` على Vercel/Firebase. راجع `.env.example`.
- المرحلة الثانية (تحليل سلوكي لأدوات المحادثة): ردود بتتكتب مباشرة (streaming) مع خطوات التنفيذ، واقتراحات للمتابعة، وتقييم 👍/👎 بيتحول لفجوات معرفة الإدارة بتسدها، وذاكرة الزائر مع «ماذا تعرف عني؟» و«امسح بياناتي»، وإدخال وقراءة بالصوت، ومساعد إداري بيخطط وبيكتب تقارير، وإشعارات Webhook موقّعة. التفاصيل في [`AI_TOOLS_REVERSE_ENGINEERING.md`](AI_TOOLS_REVERSE_ENGINEERING.md).

## بيئة استقبال التحديثات — Update Gateway

أي تطوير قادم من منصة أخرى (منصة تطوير، مساعد برمجي، أدوات محلية) يدخل التطبيق من ملف واحد أولاً: [`src/updates/updateGateway.ts`](src/updates/updateGateway.ts). البوابة تستلم «حزمة تطوير» (JSON تصريحي، لا كود يُنفَّذ)، وتقارنها بالموجود، ثم:

1. **التحليل والمقارنة**: لا يُثبَّت إلا الجديد فعلاً (زيادة) أو الأحدث فعلاً (ترقية بمحتوى مختلف). نفس المحتوى يُتجاهل حتى لو غيّرت المنصة رقم الإصدار، والإصدار الأقدم من المثبت يُتجاهل.
2. **قاعدة الملغيات**: أي تطوير أُلغي سابقاً يُرفض تلقائياً مهما عاد من أي منصة، وتُحتسب كل محاولة إعادة إدخال. الإلغاء الاستباقي لمعرّف لم يصل بعد مسموح، والاستعادة قرار إداري صريح.
3. **حماية بيانات المستخدمين**: صورة (snapshot) لكل مفاتيح بيانات المستخدمين في التخزين المحلي قبل التطبيق، وتحقق وردّ بعده. وأي حمولة تحاول لمس تخزين المستخدمين (حسابات، تركيبات محفوظة، محادثات، عناوين...) تُرفض بالكامل قبل التثبيت.
4. **الإدراج في سجل التحديثات**: قيد لكل حزمة مستقبلة ببصمة محتواها ونتائج عناصرها؛ الحزمة نفسها لا تعالج مرتين، والنسخة المنقحة من نفس المعرف تُعالج ويُشار إليها.
5. **التقارير**: كل استقبال يعيد تقريراً بقرار كل عنصر وسببه (ثُبّتت / ترقية / بدون تغيير / أقدم / ملغى / مرفوض / مؤجل لتبعية ناقصة).

الواجهة الإدارية: `/#admin` ← تبويب **«بيئة التحديثات»** — لصق حزمة JSON من أي منصة، تحليل مسبق دون تطبيق، ثم استقبال وتطبيق، مع إدارة المثبتات والملغيات وسجل التحديثات. الواجهة والبوابة تعملان في المتصفح على تخزين محلي خاص بهما (`sham_updates_*`) منفصل تماماً عن بيانات المستخدمين. الاختبارات في `tests/updateGateway.test.ts`.

- **ملفات أساسية اتمسحت:** السيرفر، أو الإدارة، أو المجتمع، أو الفحوصات، أو الـ workflows.

## النشر على GitHub Pages

### الخيار الموصى به: البناء الآلي من المصدر

بعد دمج فرع الإصلاح في `main`:

1. افتح **Settings → Pages → Build and deployment → Source** واختر **GitHub Actions** بدل **Deploy from a branch**.
2. افتح **Actions → Build, test and deploy Pages** ثم أعد تشغيل العملية على `main` أو شغّلها عبر **Run workflow**.
3. ستبني العملية المصدر، وتتحقق من الملفات، ثم تنشر artifact المجرّب. لا تنشر فروع العمل أو طلبات الدمج للموقع العام.

لم يتم تغيير إعداد Pages العام أو نشر/دمج فرع العمل خلال المراجعة. الـworkflow يعطي رسالة واضحة إذا لم يتغير إعداد Pages إلى GitHub Actions؛ لا يسمح بنشرين متنافسين من إعدادات الفرع والعمل الآلي.

المسار الافتراضي هو `/<اسم المستودع>/`. للمجال المخصص أو مستودع موقع المستخدم، اضبط Repository Variable باسم `PAGES_BASE_PATH` إلى `/`. وللبناء المحلي المقابل:

```bash
PAGES_BASE_PATH=/ npm run build:pages
PAGES_BASE_PATH=/ npm run check:pages
```

### إبقاء الإعداد القديم: main/docs

إذا اخترت عدم الانتقال إلى GitHub Actions، أعد البناء يدويًا مع كل تغيير، ثم ارفع **المصدر وملفات `docs` معًا** عبر فرع العمل وطلب دمج إلى `main`:

```bash

```

ملفات `docs` موجودة في Git للحفاظ على التوافق مع النشر القديم. `dist` و`node_modules` لا تُرفع.

> GitHub Pages يستضيف الواجهة الثابتة فقط ولا يشغّل `server.ts`. عشان الشات بوتات تشتغل عليه، الـ workflow بيبني النسخة الثابتة بـ `VITE_API_BASE_URL`، فالواجهة بتكلّم خادم Vercel مباشرة. القيمة جاية من متغير المستودع `PAGES_API_BASE_URL`، والافتراضي `https://sham-perfume-49bf.vercel.app`.

> مفاتيح الذكاء الاصطناعي بتفضل على Vercel وعمرها ما توصل للمتصفح.

## نشر الواجهة وAPI معًا على Vercel

نجاح نشر Vite إلى `dist` وحده لا يشغّل شاهين. هذا المشروع يستخدم **Build Output API v3** لبناء الواجهة ودالة Node.js في نشر واحد، ولا يحتاج اختيار Express preset أو وضع Vite داخل الدالة.

- `server/app.ts`: تطبيق Express والمسارات فقط، بلا `listen` وبلا Vite.
- `server.ts`: تشغيل محلي/استضافة Node.js تقليدية؛ ليس مدخل دالة Vercel.
- `server/vercel-entry.cts`: مدخل دالة Vercel؛ يُجمع بواسطة esbuild إلى حزمة CJS مستقلة.
- `scripts/build-vercel.mjs`: يضع الواجهة في `.vercel/output/static` والدالة في `.vercel/output/functions/api.func`، مع توجيه كل `/api/...` إلى الدالة **قبل** fallback الواجهة. الملفات المولدة لا تُرفع إلى Git.
- `tsconfig.json` يفحص السيرفر بأنواع Node، و`tsconfig.app.json` يفحص الواجهة بأنواع `vite/client`، لتجنب خلط أنواع Vite بتجميع السيرفر.

### خطوات النشر للمشروع الموجود

1. ادمج طلب الإصلاح في `main` أولًا. لا تحذف مشروع Vercel أو تنشئ مشروعًا جديدًا.
2. افتح مشروع **`sham-perfume-49bf`**، وهو المشروع المرتبط بالرابط `https://sham-perfume-49bf.vercel.app`، وليس المشروع الآخر `sham-perfume`.
3. في **Settings → Build and Deployment**: اجعل **Framework Preset = Other**، و**Root Directory = ./**، و**Node.js Version = 22.x**. لا تستخدم preset Vite أو Express. إعدادات الأوامر تأتي من `vercel.json`؛ ألغِ أي overrides قديمة خصوصًا Output Directory = dist. عند الحاجة لإدخال الأوامر يدويًا:
   - Install Command: `npx --yes bun@1.4.3 install --frozen-lockfile`
   - Build Command: `npm run build:vercel`
   - Output Directory: لا تحدد `dist` أو `docs`؛ اتركه افتراضيًا/بلا override لأن النتيجة هي `.vercel/output`.
4. في **Settings → Environment Variables** أضف `GEMINI_API_KEY` بمفتاح جديد صالح، واختر **Production**؛ اختر **Preview** فقط إن أردت اختبار نشر الفرع أيضًا. لا ترسل المفتاح في المحادثة، ولا تسمِّه `VITE_GEMINI_API_KEY`. مفاتيح بقية المزودين اختيارية؛ شاهين والأخبار بيشتغلوا بأي محرك مهيأ. بعد النشر افتح `/#admin` ← «الخبير شاهين» ← «اختبار الاتصال بالمحركات» للتأكد إن المفتاح صالح فعلاً. إلغاء مفتاح سبق كشفه واستبداله يتم في حساب المزود.
5. من **Deployments** انشر أحدث commit من `main` بعد الدمج. إعادة نشر deployment قديم تعيد الكود القديم، حتى لو حفظت إعدادات جديدة. عند إعادة النشر اختر **Redeploy** بدون استخدام build cache إذا ظهر هذا الاختيار.

### التحقق بعد النشر

- افتح `/api/health`: المتوقع JSON `{"service":"sham-perfume","status":"ok"}` وحالة HTTP 200. هذا يؤكد عمل الدالة فقط.
- افتح `/api/models`: المتوقع JSON بقائمة المحركات. `hasApiKey: true` يعني وجود إعداد المفتاح، **ولا يثبت صحة المفتاح أو نجاح طلب الذكاء الاصطناعي**.
- جرّب إرسال رسالة قصيرة في شاهين. نجاح `/api/chat` عبر POST مع رد من المزود هو اختبار المحادثة الفعلي؛ فتحه في شريط العنوان يرسل GET وليس اختبارًا صحيحًا.
- بدون مفاتيح، `/api/chat` و`/api/news` يعيدان 503 واضحًا بدل ردود/أخبار مصطنعة. ظهور صفحة Vercel `404 NOT_FOUND` على `/api/models` يعني أن دالة هذا الإصلاح لم تُنشر، وليس مجرد مفتاح غير صالح.

اختبارات Vercel تشغّل **حزمة الدالة المولدة خارج المشروع، دون node_modules أو .env** وتفحص GET/POST والأخطاء وإعدادات التوجيه. ليست محاكاة كاملة للبنية السحابية ولا اختبارًا لمفتاح حقيقي. GitHub Actions ينفذها مع اختبارات Pages. ذاكرة الأخبار داخل الدالة مؤقتة وقد تُمسح عند cold start أو تختلف بين النسخ؛ ليست قاعدة بيانات دائمة.

**Vercel Hobby مجاني للاستخدام الشخصي غير التجاري فقط**؛ لا تفترض أن متجرًا/استخدامًا تجاريًا مسموح على الخطة. تكلفة وحدود APIs منفصلة عن الاستضافة المجانية.

## ملاحظات Git المهمة

- `modified` في `git status` يعني تغيرًا محليًا غير مسجل في commit؛ لا يكفي وحده لتحديد ما إذا كانت commits سابقة قد رُفعت.
- `Skipped` في Actions يعني خطوة أو مهمة لم تُنفّذ، غالبًا بسبب شرط؛ لا يعني أن Git تجاهل ملفات عند الرفع.
- افحص الفرع الذي تنشر منه الاستضافة فعلًا. لا يلزم العمل مباشرة على `main`: يُفضّل الإصلاح في فرع العمل ثم طلب دمج، وتظل نسخة الموقع كما هي حتى الدمج والنشر.
- أوامر Git منفصلة، وليست أمرًا واحدًا متصلًا:

```bash
git add <files>
git commit -m "Describe the change"
git push origin <your-working-branch>
```

## مجتمع شام — الإدارة وبوابة التجار وبوابة المستخدمين والسوشيال

المجتمع (`#community` في الموقع وتبويب «المجتمع» في لوحة الإدارة) محتاج قاعدة بيانات حقيقية، لأن ذاكرة Vercel بتتمسح.

| المتغير (في Vercel → Settings → Environment Variables) | لازمته |
| --- | --- |
| `DATABASE_URL` (أو `POSTGRES_URL` أو `SHAM_DATABASE_URL`) | قاعدة Postgres. أسهل طريقة: Vercel → Storage → Neon → Connect للمشروع، وهي بتضيف المتغير لوحدها. |
| `SHAM_DATA_KEY` (اختياري) | من غيره السيرفر بيعمل مفتاح تشفير عشوائي لوحده ويحفظه في قاعدة البيانات. لو اتضاف بعد كده (24 حرف أو أكتر)، المفتاح المحفوظ بيتقفل بيه، فنسخة من قاعدة البيانات لوحدها متفتحش حاجة. بعد ما يتضاف **متغيّروش**. |
| `SHAM_ADMIN_TOKEN` | كلمة دخول لوحة الإدارة. هي نفسها اللي بتفتح تبويب «المجتمع». |
| `SHAM_COMMUNITY_DEV_DB` | للتجربة المحلية فقط: `memory` أو مسار فولدر (PGlite)، من غير Postgres. |

- لو قاعدة البيانات مش متوصلة، الـ API بيرد `503 COMMUNITY_NOT_CONFIGURED` والموقع بيعرض رسالة «لسه بيتجهّز» من غير ما يقع.
- الأمان: كلمات المرور scrypt، والجلسات مخزنة كـ hash (30 يوم)، والبريد والموبايل والعناوين وبيانات الدفع وروابط المورّدين والرسايل مشفرة AES-256-GCM. الإدارة بس هي اللي بتشوفها، وقراءة أي محادثة لازم يتكتب لها سبب وبتتسجل في سجل التدقيق.
- **حسابات الأعضاء — دراسة جوجل/آبل/ميتا (2026-10-18):** تأكيد البريد بكود، «نسيت كلمة المرور» بكود على البريد، رفض كلمات المرور الشائعة (قائمة Top-10k مضمّنة)، قفل الحساب بعد 5 محاولات غلط، التحقق بخطوتين (TOTP) مع بوابة دخول معلقة، **مفتاح المرور (Passkey — البصمة/الوجه)**، تنبيه كل تسجيل دخول جديد، إدارة الأجهزة (عرض/إلغاء)، «فحص أمان الحساب» في بوابتي، وسجل أحداث أمنية لكل عضو. كله في [`SHAM_AUTH.md`](SHAM_AUTH.md) — و**من غير مفاتيح جديدة**: الإرسال بيستخدم `RESEND_API_KEY` أو `SENDGRID_API_KEY` أو `SHAM_WEBHOOK_URL` لو متوفرة، ولو لأ الخدمة بتقول الصدق (503) وكل حاجة التانية شغالة.
- منتجات التجار: سعر البيع = سعر التاجر × 1.5 + الشحن حسب الدولة. أي منتج بيستنى موافقة الإدارة قبل النشر، وروابط وأرقام التواصل بتتشال من النص العام.
- الاختبار: `tests/community.test.ts` بيشتغل على PGlite في الذاكرة.
- تشغيل محلي: `SHAM_COMMUNITY_DEV_DB=memory SHAM_ADMIN_TOKEN=<كلمة> npm run dev`

## الخبير شاهين — الإعدادات والسلوك

**مكان الإعدادات (واحد للموقعين):** موقع GitHub Pages وموقع Vercel `sham-perfume-49bf` بيكلّموا نفس الخادم، فأي إعداد لشاهين بيتطبّق على الاتنين مع بعض.

1. **الأساس الدائم:** `server/config/shaheen.ts` (`SHAHEEN_SITE_SETTINGS`): المحركات المسموحة وترتيب «تلقائي»، واسم النموذج لكل محرك، ودرجة الإبداع، وأقصى طول للرد، وتعليمات إضافية، وتفعيل شاهين، والسماح للزائر باختيار محرك. بيتنشر مع الكود.
2. **التعديل من اللوحة:** `/#admin` ← تبويب **«الخبير شاهين»**. التعديل بيشتغل فوراً، وفيه زر «اختبار الاتصال بالمحركات» بيبعت طلب صغير حقيقي لكل محرك ويقول مين شغال وليه لأ. التعديل بيتحفظ بس لو مختلف عن الملف، و«رجوع لإعدادات الملف» بيلغيه.
   - على Vercel من غير `SHAM_STORE=firestore` التخزين مؤقت، والتعديل ممكن يضيع عند cold start (اللوحة بتنبّه). عشان يفضل دائم: فعّل Firestore، أو انسخ «الإعداد الدائم» من اللوحة للملف في (1).
3. **المفاتيح:** في متغيرات الخادم فقط (`GEMINI_API_KEY`، `DEEPSEEK_API_KEY`، `OPENAI_API_KEY`، `ANTHROPIC_API_KEY`، `OPENROUTER_API_KEY`، `PERPLEXITY_API_KEY`، أو `SHAM_LLM_BASE_URL` لنموذج مفتوح). مفيش مفتاح بيوصل للمتصفح، والمحرك من غير مفتاح بيختفي من واجهة الزوار.

**السلوك:**
- النافذة العائمة وصفحة «خبير المعمل» بيستخدموا سجل واحد وحالة إرسال واحدة. مسح السجل بيلغي الطلب الجاري.
- **تلقائي** بيجرّب المحركات بالترتيب ويتخطى غير المهيأ أو اللي فشل. المهلة 28 ثانية للمحاولة و50 ثانية إجمالاً، والرد بيتنسب للمحرك اللي ردّ فعلاً. اختيار محرك معيّن مش بيتبدّل سراً بمحرك تاني. لو الإدارة قفلت «السماح للزائر باختيار محرك»، كل الطلبات بتمشي تلقائي.
- الردود بتتعرض Markdown (عناوين، ونقاط، وجداول نِسب). كتلة `sham-formula` بتتحوّل لبطاقة «تحويل للحاسبات» بدل JSON خام. الرسائل الطويلة في السياق بتتقصّ وتفضل الوصفة الأخيرة محفوظة، فمش بيتمسح سجل المحادثة.
- **صور وفيديوهات وجداول للتوضيح:** شاهين بيعرض المقارنات والنِّسب في جداول. ولما الصورة أو الفيديو يفيدوا فعلاً (شكل مادة خام، نبات، أداة، طريقة تقطير أو نقع) أو يطلبهم الزائر، بيضيف في آخر الرد كتلة مخفية `sham-media` فيها **مواضيع بحث بس**، من غير روابط، لأن النماذج بتألّف روابط. الموقع بيدوّر عليها عن طريق `GET /api/media?type=image|video|place&q=` (حد 40 طلب في الدقيقة لكل زائر، ونتيجة كل موضوع بتتخزن يوم):
  - **الصور** من Wikimedia Commons وبتظهر باسم المصوّر والترخيص ورابط المصدر. مش محتاجة مفتاح، وبتتفلتر بالنوع والحجم وكلمات غير لائقة.
  - **الخريطة:** لو السؤال فيه أماكن، زي منشأ مادة خام أو مزارع الورد والعود أو مدن ومتاحف وأسواق العطور، شاهين بيكتب لحد 5 أماكن (`places`). الخادم بيجيب إحداثياتها من OpenStreetMap عن طريق Nominatim، ولو مش متاح بيستخدم Photon، بطلب واحد في الثانية والنتيجة بتتخزن أسبوع. وبتظهر خريطة تفاعلية (Leaflet بيتحمّل بس لما يكون فيه أماكن) عليها علامات مرقّمة، وتحتها أسماء الأماكن، والضغط على أي اسم بيروح للمكان على الخريطة. المكان اللي مش معروف بيظهر كرابط بحث في OpenStreetMap. مش محتاجة مفتاح.
  - **الفيديو** من YouTube Data API v3 مع `safeSearch=strict`، وبيشتغل بالضغط من غير كوكيز (`youtube-nocookie`). المفتاح `YOUTUBE_API_KEY`، ولو مش موجود بيستخدم `GEMINI_API_KEY` بشرط إن YouTube Data API v3 متفعّلة في نفس مشروع Google Cloud. لو مفيش مفتاح شغال بيظهر زر «شاهد على YouTube» بنتيجة البحث.
- الأخطاء بتظهر كفقاعة خطأ واضحة فيها زر «إعادة المحاولة»، ومش بتدخل في سياق النموذج.
- حد السؤال 4000 حرف، والسياق 24 رسالة/16000 حرف. معدل الرسائل `SHAM_SHAHEEN_RATE_PER_MIN` (الافتراضي 10 لكل زائر في الدقيقة) بيرجّع 429، والزائر بيتعرّف بمعرّف مجهول من المتصفح (`X-Sham-Visitor`) مش بالـ IP بس، علشان مستخدمين شبكة الموبايل الواحدة ما يتحجبوش مع بعض (التفاصيل تحت).
- **أخبار العطور:** التحديث بيستخدم أول محرك شاهين متاح (مش Gemini بس). المقالات عليها تنبيه إنها تحريرية مولّدة بالذكاء الاصطناعي. التحديث اليدوي بيرجّع نسخة مخزنة لمدة 10 دقائق، وأقصاه 3 مرات في الساعة لكل IP.
- لا تُستخرج وصفة من مجرد كلمات مثل «زيت» أو «كحول». النقل للحاسبة بيحتاج كتلة `sham-formula` صالحة ومجموع نوتات 100%. المقترح التجريبي مش شهادة IFRA.

**حدود التحقق:** اختبارات تكامل حقيقية لخادم HTTP واختبارات محلية باستجابات مزودي خدمات محاكاة؛ يلزم اختبار مفاتيحك الفعلية على استضافة Node.js. لا توجد مفاتيح خدمة مُضافة إلى المشروع، وGitHub Pages وحده لا يشغّل المحادثة.

## نمو شاهين — كشّاف المصادر ومهارات القراءة ومدرسة الاعتماد على النفس

كل 6 ساعات (`.github/workflows/shaheen-discover.yml`):

1. **كشّاف المصادر** (`scripts/shaheen-discover/`) بيدوّر على متاجر عطور أونلاين: بحث على الويب بالذكاء الاصطناعي طول ما الباقة متاحة، ولوحده من غيرها (دفتر متاجر معروفة، المتاجر الرسمية للماركات اللي بنبيعها، والمواقع اللي بتضيفها في متغير `DISCOVER_SEEDS`). كل متجر بيتفحص بأدب: بيحترم `robots.txt` وسرعة الموقع، ومش بيقرب من الأسواق الكبيرة (أمازون ونون…) ولا السوشيال ولا مواقع المراجعات. بيقرا خريطة المنتجات، ولو مفيش بيتصفح صفحات الأقسام، وبيختار لغة واحدة للمتاجر متعددة اللغات، ويقرا 6 صفحات منتجات بدون ذكاء اصطناعي. المتجر بيتقبل لو نص الصفحات على الأقل مقروءة وأغلبها عطور وبعملة واحدة. النتيجة في `src/data/live/import-sources.json`، وأقصى عدد مصادر نشطة يتحدد بـ `DISCOVER_MAX_ACTIVE` (افتراضي 20). ولو عايز تمنع متجر حطه في `DISCOVER_BLOCK`.
   - **من العالم كله:** البحث بيلف على المناطق بالدور — الخليج والعالم العربي، أوروبا، الأمريكتين، شرق آسيا، وسط آسيا — وكل منطقة بلغتها (عربي، فرنساوي، ألماني، إسباني، إيطالي، بولندي، تركي، روسي، ياباني، كوري، صيني) وبالإنجليزي. ودفتر المتاجر المعروفة فيه متاجر عطور كبيرة من كل منطقة، 6 جداد كل جولة بالتناوب. كل متجر بيتسعّر بعملته (يورو، جنيه إسترليني، ين…) بسعر الصرف اليومي، وبنفس قاعدة التسعير (+50% + الشحن).
   - **السيرة الذاتية للمتجر قبل ما يدخل** (`scripts/shaheen-discover/trust.ts`): درجة ثقة من 100 — عمر النطاق من السجل الرسمي (RDAP)، اتصال آمن، بيانات التواصل (بريد/هاتف/صفحة تواصل)، هوية الشركة (سجل تجاري، رقم ضريبي، Impressum، عنوان)، سياسة الإرجاع والشحن (وهل بيشحن دولياً) والخصوصية والشروط، وسائل دفع معروفة، منصة متاجر معروفة، حسابات رسمية، وضمان إن المنتجات أصلية. أقل من 60 = مرفوض (بيتراجع تاني بعد شهر). وأي علامة خطر بترفضه نهائياً مهما كانت درجته: نطاق عمره أقل من 6 شهور، من غير https، بيبيع تقليد («dupe / inspired by / تقليد») سواء في الصفحة الرئيسية أو أسماء المنتجات، دفع بالحوالات بس، أو موقع Google مصنّفه خطر (لو ضفت السر الاختياري `SAFE_BROWSING_API_KEY`). المتاجر النشطة بتتراجع سيرتها كل أسبوع. ولو في متجر إنت ضامنه بنفسك وسيرته ضعيفة لأن موقعه مش بيعرض بياناته (زي سياسة الإرجاع)، اكتب اسمه في المتغير `DISCOVER_TRUSTED` — سيرته بتتقري وتظهر عادي، بس الدرجة الضعيفة مش بتوقفه (علامات الخطر بتوقفه برضه). ولو صفحة سياسة ممنوعة على القراءة الآلية في `robots.txt` بتتحسب «مقدرش أتأكد» بنص الدرجة لو الموقع عمره 3 سنين أو أكتر، والموقع الرسمي للماركة نفسها (نطاقه هو اسم الماركة بالظبط ومن سنين) بيتحسب هوية معروفة ومنتجات أصلية. والسيرة كاملة (الدرجة وكل بند ✓/✗) بتظهر في لوحة الإدارة ← تبويب شاهين ← «نمو شاهين».
2. **مستورد شاهين** (`shaheen-import.yml`) بيستورد من المتاجر المقبولة بنفس المنهجية: السعر + 50%، تنظيف الصور، وصف عربي، مراجعة كل صفحة. العطور بس (`perfumeOnly`). ولو نفس العطر موجود عند مورد تاني ما بيتكررش، بيتحفظ كعرض بديل (`altOffers`). الحدود: `IMPORT_MAX_TOTAL` و`IMPORT_MAX_PER_SOURCE`.
3. **مهارات القراءة** (`scripts/shaheen-import/{generic,skills}.ts`): ترتيب القراءة بيبدأ بـ JSON-LD، بعده مهارة اتعلمها للمتجر، بعده القارئ الذاتي (OpenGraph/microdata/WooCommerce)، وآخر حاجة الذكاء الاصطناعي. كل قراءة صحيحة بالذكاء الاصطناعي بتعلّم شاهين مكان الاسم والسعر والصورة في المتجر ده، فيقرا باقي صفحاته لوحده (`src/data/live/shaheen-skills.json`).
4. **مدرسة شاهين** (`scripts/shaheen-school/`): بيمتحن نفسه على أسئلة العطور والموقع. اللي يقدر يتعلمه من مكتبته بيتعلمه من غير ذكاء اصطناعي، والباقي بيذاكره مع أي محرك متاح (`SCHOOL_MAX_STUDY` سؤال في كل جولة) ويحفظه في ذاكرته بصيغ مختلفة. الذاكرة دي هي اللي الموقع بيرد منها لو كل خدمات الذكاء الاصطناعي وقفت، وده على GitHub Pages كمان. التقرير في `src/data/live/shaheen-school.json`.

كل ده بيظهر في لوحة الإدارة، تبويب «الخبير شاهين»، تحت عنوان «نمو شاهين».

## منارة شاهين — المندوب الإعلامي وخبير SEO

«منارة شاهين» وكيل الظهور في محركات البحث، ويعمل تحت قيادة «الخبير شاهين». مش بيدّعي إنه بيضمن الترتيب الأول؛ بيعمل اللي بيوصّل ليه بطريقة بيضاء وقابلة للقياس: يفحص الموقع الحقيقي، يدرس منهجية SEO، يكتب عناوين وأوصافاً مفحوصة، ينشرها في صفحات ثابتة، يرسل الروابط للمحركات، ثم يقيس ويتعلم.

**الدورة (كل 6 ساعات — `.github/workflows/shaheen-seo.yml`، أو يدوياً من اللوحة):**
1. **فحص حقيقي** للموقع المنشور: robots وsitemap والصفحة الرئيسية وصفحات الأدوات والمنتجات (canonical، hreflang، og/twitter، البيانات المنظمة، طول العنوان والوصف، alt الصور، الروابط الداخلية، الحجم والاستجابة). النتيجة تقييم من 100 وملاحظات مرتّبة بالخطورة (`critical` 12، `major` 5، `minor` 1.5).
2. **دراسة درس من المنهج**: 12 مجالاً و24 درساً (أساسيات الزحف، العناوين والأوصاف، البيانات المنظمة، المحتوى، الروابط الداخلية، الأداء، الفهرسة، IndexNow، llms.txt، التحليل، الأخلاقيات، القياس). الدرس الأضعف مجالاً يُعاد تطبيقه بعد إتمام المنهج.
3. **تحسين النصوص**: عنوان 50–60 حرفاً ووصف 130–160 لصفحتين كحد أقصى في الدورة، بشرط العربية الواضحة، وعدم ذكر أي شركة أو نموذج ذكاء اصطناعي، وعدم اختراع أرقام أو شهادات أو جوائز، وعدم استخدام «الأفضل» أو الوعود المطلقة أو الروابط أو HTML.
4. **تقييم شاهين**: يقيّم الدورة من 10 ويكتب توجيهات، لكن سلم الثقة حتمي: **تدريب** (يقترح فقط) → **توجيه** → **اعتماد على النفس**، ولا ينتقل إلا بعد عدد دورات ودروس وتقييم فحص وتقييم شاهين، وأي هبوط بعد تغيير منشور يرجّع آخر تغيير تلقائياً.
5. **تقرير المندوب الإعلامي** كل 20 ساعة على الأقل، و**إرسال** الصفحات المتغيّرة إلى المحركات عند `SEO_SUBMIT=1`.
6. **حفظ الحالة** في `src/data/live/seo-agent.json` والنصوص المنشورة في `src/data/live/seo-pages.json` (يرفعها `scripts/ci/publish.mjs` ثم يعيد بناء Pages).

**ملفات SEO التي يبنيها الموقع** (`scripts/seo-build.mts` بعد `vite build`):
- `tools/*.html`: صفحة HTML ثابتة كاملة لكل أداة من أدوات الموقع (12 صفحة) بعنوان ووصف وh1 ومقدمة وخطوات وأسئلة شائعة وروابط داخلية، مع `WebApplication` و`BreadcrumbList` و`FAQPage`.
- `sitemap.xml` (الصفحة الرئيسية + الأدوات + صفحات المنتجات)، و`robots.txt` يسمح بالزواحف البحثية وزواحف البحث بالذكاء الاصطناعي ويحجب `/api/` فقط، و`llms.txt`، و`feed.xml`.
- `/<IndexNow key>.txt` للتحقق من ملكية الموقع، وملفات التحقق من Google/Bing عند ضبط متغيراتها.
- حقن وسوم `<head>` في الصفحة الرئيسية (canonical، hreflang، og/twitter، JSON-LD: Organization + WebSite + WebApplication + ItemList) بشكل متكرر لا يضاعف الوسوم، مع تحديث `404.html` ليبقى مطابقاً.

**الإرسال لمحركات البحث:**
- **IndexNow** فوراً لـ Bing وYandex وNaver وSeznam وYep (وDuckDuckGo/Ecosia/Yahoo عبر فهرس Bing)، بحد أقصى 200 رابط في الدفعة وبتأجيل إن لم يوجد جديد كافٍ.
- **Bing Webmaster API** عند وجود `BING_WEBMASTER_API_KEY`.
- **Google** لا يشترك في IndexNow، ونقطة `sitemap ping` القديمة أُغلقت سنة 2023؛ لذلك يعتمد على `sitemap.xml` + `feed.xml` المعلنتين في `robots.txt` + ملف التحقق، ورفع الخريطة تلقائياً عبر Search Console عند وجود `GSC_SERVICE_ACCOUNT_JSON` (اختياري).

**الظهور من غير حساب Search Console (كل ده شغال تلقائياً):**

أول حاجة: Search Console نفسه **مجاني** ومش محتاج بطاقة، وما فيش اشتراك مدفوع. اللي بيطلب بطاقة هو مشروع Google Cloud لو حبيت تشغّل الـAPI بحساب خدمة — وده اختياري بالكامل. الوكيل مش متوقف عليه:

1. **الخريطة في robots.txt:** `sitemap.xml` بتتبني مع كل نشر وبتتعلن، ومعاها `lastmod` حقيقي لكل رابط.
2. **الخلاصة كخريطة تانية:** `feed.xml` معلنة كـ`Sitemap:` تانية؛ محركات البحث بتقبل خلاصات RSS كخرائط، فده اكتشاف مستقل عن الخريطة الأساسية.
3. **إشعار WebSub:** الخلاصة فيها `<atom:link rel="hub">`، والوكيل بيبعت `hub.mode=publish` لمحاور عامة **بس لما محتوى الخلاصة يتغيّر فعلاً** (بصمة FNV-1a بتمنع الإشعارات المكررة). مش إرسال فهرسة، لكنه بيبلّغ القارئ بالتحديث قبل الزحف الجاي.
4. **IndexNow مباشرة:** لو نقطة التجميع `api.indexnow.org` وقعت أو رفضت الدفعة، الوكيل بيجرّب المحركات نفسها بالترتيب (Bing → Yandex → Seznam → Naver → Yep) لحد أول قبول، والنتيجة بتتسجل في `state.submissions`.
5. **فحص وصول الزاحف:** كل دورة بتطلب الرئيسية وصفحة الأدوات وأول أداة **بمعرّف Googlebot** وتفحص رمز الاستجابة و`X-Robots-Tag` و`<meta name="robots">`. ده بيكشف أي حاجز فهرسة من برّه الموقع — نفس اللي بيبان في تقرير التغطية، لكن من غير حساب. النتيجة في اللوحة: «فحص وصول الزاحف 3/3».
6. **قياس الأداء بلا مفتاح:** `probePageSpeed` بيقرأ Lighthouse العام (جوّال: أداء/SEO/إتاحة/أفضل الممارسات + LCP وCLS وTBT) مرة كل 24 ساعة كحد أقصى، بديل لتقرير Core Web Vitals في لوحة المالك.

**عنوان واحد لمحركات البحث:** الموقع الأساسي هو GitHub Pages، وكل الصفحات (من البناءين) بتشاور عليه بـ canonical (`SITE.url` في `src/seo/site.ts`)، عشان نسخة Vercel ما تنافسش الموقع الأساسي في نتائج البحث. و«منارة شاهين» بتفحص الموقع الأساسي (`SEO_SITE_URL`). ولو أي عنوان بيعرض صفحة التطبيق بدل صفحات الأدوات والمنتجات، الفحص بيكتبها ملاحظة واحدة واضحة: «النسخة المنشورة قديمة».

**مهم — بناء Vercel:** بوابة `scripts/vercel-ignore.sh` كانت تتخطى البناء على الفرع الرئيسي، فوصل الأمر أن النطاق الأساسي `sham-perfume-49bf.vercel.app` ظل يخدم نسخة قديمة (بلا robots/sitemap/llms وبنفس العنوان لكل المسارات — سجّل الفحص الحي 1/100 عليه). صار المشروع الرئيسي **يبني دائماً**؛ والثاني (غير المستخدم) وحده يتخطى. لو ظل النطاق قديماً بعد الدمج، افحص في لوحة Vercel: Settings ← Build & Development Settings ← **Ignored Build Step** لازم يكون فارغاً (إعداد اللوحة يتفعّل على `vercel.json`)، ثم Deployments ← آخر نشر ← ⋯ ← **Redeploy** مع إلغاء الكاش.

**تفعيل Search Console (مجاني — والملف جاهز في المستودع):**

Search Console نفسه مجاني بالكامل ومش محتاج بطاقة؛ اللي بيطلب بطاقة هو مشروع Cloud لو حبيت API بحساب خدمة. الملف اللي جوجل أصدرته للموقع اتحفظ في `public/google7ef3d5aa6cf98197.html`، وبيتبني في جذر `docs/` و`dist/`، فالخطوات:

1. افتح `https://search.google.com/search-console` وسجّل الدخول بحساب Google عادي.
2. أضف خاصية من نوع **بادئة عنوان URL** (URL prefix) — مش «Domain»؛ خاصية الـDomain تحتاج سجل DNS مش متاح على `github.io`.
3. أضف الرابطين كخاصيتين منفصلتين (لكل واحدة ملف تحقق خاص بها عند جوجل):
   - `https://spculculat-oss.github.io/Sham-Perfume/` (الموقع الأساسي، وهو العنوان canonical لكل الصفحات)
   - `https://sham-perfume-49bf.vercel.app/` (المحرك؛ صفحاته الثابتة بتشاور على الموقع الأساسي)
4. اختار طريقة التحقق **ملف HTML**؛ جوجل هتقرأ `/google7ef3d5aa6cf98197.html` مباشرة من جذر الموقع بعد النشر. (لو جوجل أصدرت ملفاً بتوكن مختلف، حطّه في `public/` بنفس الاسم وسجّله في `SITE.googleVerification` — والاختبارات هتمنع أي تعارض.)
5. بعد التحقق: **Sitemaps** ← أضف `sitemap.xml` ثم `feed.xml`. جوجل هتقرأ الخريطتين تلقائياً بعد كده، ومش محتاج أي ping.
6. **URL Inspection** ← اطلب فحص الرئيسية وصفحات الأدوات واضغط «طلب فهرسة» — ده المسار الرسمي الوحيد لإرسال رابط بعينه لجوجل من غير IndexNow.

لو حبيت أتمتة رفع الخريطة بعد كده: أنشئ حساب خدمة في Google Cloud وشاركه في Search Console كـ«Full» ثم ضع `GSC_SERVICE_ACCOUNT_JSON` و`GSC_SITE_URL`. اختياري تماماً؛ الملفات والخريطة بتشتغل من غيره.

**اللي محتاج حساب فعلاً (ومش موجود هنا):** عدد الظهور والنقرات، كلمات البحث اللي جابت زوار، وتغطية الفهرسة التفصيلية. دي بيانات مالك الموقع، ومفيش طريقة شريفة للحصول عليها من برّه. لو حبيتها بعدين: Search Console مجاني (تحقّق بملف أو وسم، والوكيل بيحط الملف تلقائياً لو ضفت `GOOGLE_SITE_VERIFICATION`)، أو Bing Webmaster Tools (مجاني وبيدعم الاستيراد من Search Console).

**في اللوحة:** `/#admin` ← تبويب **«منارة شاهين»**: التقييم والملاحظات والمرحلة والدروس والخطوات القادمة وحالة المحركات وقنوات الظهور بلا حساب (WebSub + فحص الزاحف + الأداء) وتقرير المندوب وتقييم شاهين، وزر «تشغيل دورة الآن» (مع خيار الإرسال). الـAPI: `GET /api/admin/seo` و`POST /api/admin/seo/run` (202، و409 لو فيه دورة شغالة، بحد 4 تشغيلات كل 10 دقائق). وللعموم: `GET /api/seo/status` و`/sitemap.xml` و`/robots.txt` و`/llms.txt` و`/feed.xml` و`/<key>.txt`.

**التشغيل المحلي:**


**المتغيرات:** `SEO_SITE_URL` (الأصل الأساسي)، `SEO_SUBMIT`، `SEO_ENGINE_ORDER`، `WEBSUB_HUBS` (اختياري؛ محاور إشعار الخلاصة) (ترتيب المحركات، والافتراضي `gemini,deepseek,openai,claude,openrouter,self_hosted` بعد استبعاد غير المهيأ)، `GSC_SERVICE_ACCOUNT_JSON` و`GSC_SITE_URL`، `BING_WEBMASTER_API_KEY`، `GOOGLE_SITE_VERIFICATION`، `BING_SITE_VERIFICATION`. كلها اختيارية، ومنها كل حساب Search Console/Bing؛ من غير أي مفتاح يظل الوكيل يفحص ويدرس ويبني الملفات، ومن غير IndexNow/فهارس يظل كل شيء صادقاً.

## السعة والزوار المتزامنون

شاهين مصمم يستقبل أكتر من 1000 زائر في نفس اللحظة. الطبقة دي في `server/core/capacity.ts`:

1. **ذاكرة إجابات** لأول سؤال في المحادثة (الأسئلة الجاهزة وأسئلة زي «الفرق بين EDP وEDT»): السؤال بيتطبّع (تشكيل، همزات، علامات، حروف كبيرة/صغيرة) و100 زائر بيسألوا نفس السؤال في نفس اللحظة = **نداء واحد** للمزوّد. أسئلة المتابعة (اللي فيها سياق) ما بتتخزنش أبدًا. أي تغيير في الإعدادات من لوحة الإدارة بيوصل فورًا.
2. **بوابة المزوّدين**: حد أقصى للنداءات المتزامنة، ولما المزوّد يرد 429 (الحصة خلصت) البوابة بتوقف النداءات عليه للمدة اللي طلبها، وبتتعلم سرعته (AIMD) بدل ما تكرر الطلبات المرفوضة. الزائر بيستنى في الطابور لحد `SHAM_QUEUE_WAIT_SECONDS` وبعدين يا إما ياخد الإجابة، يا إما رد صادق `503 SHAHEEN_BUSY` مع `Retry-After`.
3. **المتصفح** بيعيد المحاولة لوحده 3 مرات حسب `Retry-After` ويعرض «شاهين مشغول حاليًا، سؤالك في الدور…» بدل رسالة خطأ.
4. **حدود عادلة**: الحد لكل زائر (معرّف مجهول في `localStorage`)، وسقف أعلى لكل IP، فمئات الزوار ورا IP واحد (شبكات الموبايل في مصر) ما يتحجبوش.
5. قائمة موديلات Gemini بتتخزن 10 دقايق بدل ما تتطلب مع كل سؤال، و`vercel.json` فيه `"fluid": true` (Fluid compute: نسخة واحدة من الدالة بتخدم طلبات كتير في نفس الوقت).

| المتغير | الافتراضي | المعنى |
|---|---|---|
| `SHAM_ANSWER_CACHE_MINUTES` | 360 | مدة حفظ إجابة أول سؤال (0 = إيقاف) |
| `SHAM_ANSWER_CACHE_ENTRIES` | 2000 | أقصى عدد إجابات محفوظة |
| `SHAM_PROVIDER_MAX_CONCURRENT` | 300 | أقصى نداءات متزامنة للمزوّدين (حتى 900؛ Vercel بيسمح بـ 1024 اتصال للنسخة) |
| `SHAM_QUEUE_WAIT_SECONDS` | 20 | أقصى انتظار في الطابور قبل `SHAHEEN_BUSY` |
| `SHAM_SHAHEEN_RATE_PER_MIN` | 10 | رسائل لكل زائر في الدقيقة |
| `SHAM_SHAHEEN_RATE_PER_IP_MIN` | 300 | سقف الرسائل لكل IP في الدقيقة |
| `SHAM_PER_VISITOR_CONCURRENT` | 2 | طلبات الزائر الواحد عند المزوّدين في نفس اللحظة (مسار لكل زائر؛ والدور للأقل استخدامًا في آخر دقيقة) |
| `GEMINI_LITE_MODEL` | `gemini-flash-lite-latest` | الموديل الخفيف للأسئلة البسيطة القصيرة (حصة منفصلة وأسرع) |
| `SHAM_LITE_ROUTING` | مفعّل | `off` لإيقاف توجيه الأسئلة البسيطة للموديل الخفيف |
| `SHAM_GEMINI_RPM`، `SHAM_DEEPSEEK_RPM`، `SHAM_OPENAI_RPM`، `SHAM_CLAUDE_RPM`، `SHAM_SELF_HOSTED_RPM`، `SHAM_OPENROUTER_RPM`، `SHAM_PERPLEXITY_RPM` | يتعلّم لوحده | الحصة المعروفة لكل مزوّد في الدقيقة (مثلًا من صفحة الحدود في AI Studio) |

**السرعة وتخفيف الضغط:** «تطبيقات شاهين السريعة» (`src/utils/shaheenQuickApps.ts`) بتحسب المهام البسيطة (تخفيف الكحول، كميات الزيت والكحول، أونصة↔مل، الشكر، التعريف) **في متصفح الزائر فورًا** من غير أي نداء للذكاء الاصطناعي؛ والأسئلة القصيرة البسيطة بتروح للموديل الخفيف؛ ولما حصة Gemini تخلص بيجرب Lite ثم أكبر موديل Gemma متاح على نفس المفتاح (حصته منفصلة).

**الحد الحقيقي هو حصة المزوّد مش الخادم:** حصة Gemini بتتحسب **لكل مشروع مش لكل مفتاح**، والخطة المجانية بتسمح بعدد قليل من الطلبات في الدقيقة، يعني الأسئلة **المختلفة** محدودة بالحصة دي مهما كان الخادم قوي. علشان 1000 سؤال مختلف في نفس الوقت لازم تفعيل الفوترة على مشروع Google (Tier 1) و/أو إضافة مفاتيح مزوّدين تانيين (DeepSeek/OpenAI/Claude/OpenRouter) — البوابة بتوزع الطلبات تلقائيًا على أي مزوّد متاح.

اختبار الحمل (بيشغّل الراوتر الحقيقي مع مزوّد وهمي، من غير أي نداء خارجي):

```bash
VISITORS=1000 SPREAD_S=5 PROVIDER_RPM=2000 node --import tsx scripts/load-test.mts   # حصة مدفوعة
PROVIDER_RPM=15 node --import tsx scripts/load-test.mts                              # حصة مجانية (~3 دقايق)
NAT_IPS=20 node --import tsx scripts/load-test.mts                                   # زوار ورا 20 IP بس
```

| 1000 زائر خلال 5 ثواني | قبل | بعد |
|---|---|---|
| حصة مدفوعة | 100% — 1000 نداء — وسيط 2.4ث | 100% — 412 نداء — وسيط 1.3ث |
| زوار ورا 20 IP | 20% | 100% |
| 1000 سؤال مختلف في نفس اللحظة | — | 100% — أقصى 10ث |
| حصة مجانية (15 طلب/دقيقة) | 6% — 4895 نداء للمزوّد | 83.5% — 715 نداء، والباقي `SHAHEEN_BUSY` صادق |

## طبيب شاهين — الصيانة التلقائية كل 10 دقايق

«طبيب شاهين» (`scripts/doctor/`) وكيل ذكاء اصطناعي صغير بيراجع الخبير شاهين كل 10 دقايق ويصلّح المشاكل لوحده من غير تدخل بشري. بيشتغل على أجهزة GitHub Actions (`.github/workflows/shaheen-doctor.yml`) **مش على خادم الموقع**، وكل فحص حوالي 8 طلبات خفيفة (والسؤال التجريبي بيرجع من ذاكرة الإجابات)، فالزوار مش بيحسوا بيه.

**بيفحص:** الـ API، هل الموقع على آخر نسخة من main (ولو لأ: حد النشر في Vercel؟ بناء فاشل؟)، أوضاع شاهين، سؤال تجريبي (رد فاضي؟ اسم مزوّد ظاهر؟ حصة؟)، ربط GitHub Pages بالـ API، موقع Pages، عدّادات الخادم الحقيقية (نسبة الأخطاء وزمن الرد وحالة المزوّدين — `GET /api/admin/maintenance`)، فحص وبناء main، والصور.

**بيصلّح لوحده:**

| المشكلة | العلاج |
|---|---|
| أسئلة الزوار بتفشل / الأخطاء عالية | تصفير حالة المزوّدين وقائمة الموديلات على الخادم (`POST /api/admin/maintenance`) + إعادة فحص ومزامنة المفاتيح |
| Vercel رافض النشر (الحد اليومي) | يستنى لحد ما الحد يتصفّر وبعدين يعيد النشر (بـ `VERCEL_TOKEN`) أو يعمل كومِت فاضي ينشر آخر نسخة |
| بناء Vercel فشل | يجرب البناء بنفسه: لو نجح يعيد النشر، لو فشل يصلّح الكود |
| فحص main أحمر، اسم مزوّد في الرد، CORS بايظ | **إصلاح كود بالذكاء الاصطناعي** |
| GitHub Pages واقع | يعيد تشغيل البناء والنشر |

**إصلاح الكود:** بيقرا سجل الخطأ والملفات المتعلقة، والنموذج (نفس محركات ومفاتيح شاهين) بيقترح تعديل، وبيتطبق **بس لو عدّى كل الفحوص** (`lint`، كل الاختبارات، بناء Vercel واختباره، فحص EdgeOne) — لو فشل بيبعت الخطأ للنموذج تاني (لحد 3 محاولات) ولو ما نجحش بيرجّع الملفات زي ما كانت. بعد النجاح بيعمل PR ويدمجه (أو push مباشر لو GitHub مش سامح للـ Actions تعمل PR)، ويشغّل بناء Pages، ويراقب الموقع بعد النشر: لو ظهرت مشاكل جديدة مرتين ورا بعض **بيرجّع التغيير تلقائيًا**.

**حدود الأمان (هي اللي بتخليه يشتغل لوحده بأمان):** ما بيتصرفش في مشكلة غير لما تتكرر فحصين (20 دقيقة) إلا لو بناء main أحمر؛ كل علاج له فترة تهدئة؛ أقصى 3 إصلاحات كود في اليوم وإصلاح واحد تحت المراقبة في نفس الوقت؛ ما يقدرش يعدّل كوده هو ولا الـ workflows ولا الأسرار ولا الاعتماديات ولا الاختبارات الموجودة (يقدر يضيف اختبارات جديدة)؛ أقصى 8 ملفات و400 سطر في الإصلاح الواحد.

**السجل:** issue مفتوحة بعنوان «🩺 طبيب شاهين — سجل الصيانة التلقائية» (label `shaheen-doctor`): الجسم لوحة حالة بتتحدث كل فحص، والتعليقات بس لما يحصل حاجة (علاج، إصلاح، رجوع، مشكلة جديدة، رجوع للسلامة). نفس التقرير في لوحة الإدارة ← تبويب «طبيب شاهين»، ومعاه عدّادات الخادم وأزرار العلاج اليدوي.

**الأسرار (Settings → Secrets and variables → Actions):**

| السر | بيدّي الطبيب إيه |
|---|---|
| `GEMINI_API_KEY` (أو أي مفتاح ذكاء اصطناعي تاني موجود) | إصلاح الكود |
| `SHAM_ADMIN_TOKEN` (نفس قيمته في Vercel) | عدّادات الخادم وعلاج الخادم مباشرة |
| `VERCEL_TOKEN` | إعادة النشر على Vercel فورًا |

تشغيل يدوي: Actions ← «Shaheen Doctor» ← Run workflow (`live` يصلّح، `dry` يراجع بس). محليًا للمراجعة بس: `DOCTOR_MODE=dry node --import tsx scripts/doctor/run.mts`.
